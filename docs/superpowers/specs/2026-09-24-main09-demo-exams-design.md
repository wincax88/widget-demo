# main09 全量演示考试与成绩设计

## 目标和边界

仅修改、部署 `widget-demo`，不修改 `edu-plus-2`。在当前 `main09` 租户，为全部已同步学生保存演示考试、科目和成绩，使考试管理、学生成绩页及第三方工作台的最近考试概览、各科成绩表、成绩趋势组件有数据。当前可登录且有精确身份绑定的学生能查看本人演示数据；不作为真实学业成绩使用。教师和家长组件仍遵守现有任课、亲子关系校验，本次不伪造这些关系，也不承诺它们有数据。

## 方案选择

采用持久化且隔离标记的演示数据。仅按请求临时生成组件样例不会满足“考试管理也保存考试和成绩”；直接挂到真实班级又会混淆真实教学关系。故在 `widget-demo` 内建立独立的“【演示】全体学生组”和三个演示科目，三个考试分别使用现有 `weekly`、`monthly`、`midterm` 类型，日期固定为 2026-08-20、2026-09-05、2026-09-20。标题、班级、科目均以“【演示】”开头，页面补充“演示数据，非真实成绩”提示。考试增加明确的演示标记和稳定批次键，便于识别、幂等执行及后续定向清理；不触及真实考试。

## 身份绑定

当前人员同步键为 `student:<公开 API 记录 id>`，而组件以 OIDC `identity_id` 查找人员，两者不是同一标识。`Person` 增加可空的基座用户 ID 字段；主数据同步仅从学生记录的结构化 `fields.user_id` 填充，不按姓名、学号或手机号推测。组件按租户、`STUDENT` 类型、有效状态、该用户 ID 精确查找，必须恰好命中一条；应用 Handoff 建立学生会话时也优先绑定同一条已同步人员记录。零命中时保留现有独立登录行为，但组件返回身份未同步、应用不显示演示成绩；多命中时拒绝绑定并报告冲突。非学生身份的登录行为保持现状。

## 数据生成与发布

写入工具固定目标为 `main09`，默认只预览。预览先核对租户、全部同步学生数量、已有非空 `user_id` 的唯一性、已有演示批次及拟写入数量；身份冲突时停止，不进行部分发布。经实际预检确认，244 名学生中 232 名有效且有 `user_id`、6 名有效但无 `user_id`、6 名停用。用户追加确认：全部 244 名均入库，无 `user_id` 或停用者当前不保证能通过本人账号查看组件。应用迁移并重新运行授权主数据同步后，才允许执行写入。

执行时只引用现有全部已同步学生记录，新建带固定演示键的班级、科目、录入人和学生在演示组的关系。每名学生在每场考试的三科成绩由稳定哈希生成，范围为 60–98 分，同一批次重跑值不变；按三场考试产生可见的总分变化。先写考试、科目及全部分数，核对数量后再发布；如任一步失败，目标批次保持不可见的草稿或整体回滚，不留下部分发布的考试。244 名学生对应 3 场考试、9 个考试科目、2,196 条成绩，实际以预览结果为准。重跑只能补齐同一演示批次，不覆盖真实成绩。

演示组的排名只表示本演示组内的比较，不代表学生真实班级排名；考试和组件的演示提示应使这一点可见。真实班级、真实任课及亲子关系不变。清理工具只接受已知演示批次键，并在显示目标数量后要求显式确认；本次不运行清理。

## 验证与交付

测试覆盖：`user_id` 精确绑定、缺失者仍入库、重复者拒绝、跨租户隔离、生成分数的确定性与范围、重复运行幂等、失败时不部分发布、演示标记展示、学生仅能读取自己的成绩。部署后先执行只读预览，确认人数，再写入并核对考试、科目、成绩及演示组关系数量；检查学生组件三种数据结构和考试管理列表。不能取得真实学生授权令牌时，不伪造生产令牌，最终端到端登录验收由持有测试学生账号的用户完成。

## 已知限制

三场考试属于虚构成绩，即使显著标记也会对 `main09` 的学生可见。任课和亲子关系仍未由基座公开 API 提供可靠引用，教师和家长组件可能为空。缺少 `user_id` 的 6 名学生与停用的 6 名学生仍有演示记录，但当前无法保证他们通过本人身份查看组件。
