# Widget Demo 主数据部分同步设计

## 背景与范围

`main09` 已能完成应用 Handoff，但主数据同步在任课关系处返回 502。只读核对发现：公开 API 返回的 12 条任课关系均没有教师和班级的外部引用，98 条亲子关系均没有家长和学生的外部引用；这符合基座文档中「无唯一有效外部映射时引用为 null」的读取契约。另有 349 条教师、244 条学生、79 条家长记录，目前以未加类型前缀的外部 ID 或内部数字 ID 为本地唯一键，跨身份发生键冲突。

本次只修改 `widget-demo`。不修改 `edu-plus-2`，不根据姓名、学号等字段猜测关系，不扩大现有考试和成绩访问权限。

## 方案选择

选择显式的「部分完成」同步：导入教职工、学生、家长、班级、课程五类基础数据；暂不写入任课、学生班级、亲子三类关系。继续返回泛化 502 无法表达已导入的数据；静默跳过并报告成功则会误导使用者。

## 数据流与存储

1. 继续按现有授权会话和分页规则读取八类公开主数据。五类基础数据用于导入，三类关系只计数，不写入业务表。公开 API 请求或基础数据写入失败时，同步记录仍为 `FAILED`，错误按现有方式返回。
2. 人员本地同步键统一采用 `实体类型:基座记录 ID`，例如 `teacher:123`、`student:123`；该 ID 来自公开 API 顶层 `id`，不使用可能为空、也可能跨类型重复的 `external_id`。班级和课程沿用现有同步键，本次不调整其映射。重新同步使用 upsert，重复运行不会再使不同身份覆盖同一人员行。
3. 数据库为同步运行增加 `PARTIAL` 状态。成功导入基础数据后记录 `PARTIAL`，响应使用 `status: "partial"`。`counts` 中的 `teacher`、`student`、`parent`、`class`、`course` 表示读取并导入的基础记录数；`skipped_teacher_teaching_assignment`、`skipped_student_class_relation`、`skipped_parent_student_relation` 表示未导入的关系记录数。
4. 已存在的旧人员行和登录会话不自动删除、重绑或授予关系权限。新键保证后续导入不再互相覆盖；旧数据清理由另行评估的数据迁移处理，避免破坏已有外键。由于本次不导入关系，登录会话与基础主数据也不据此获得任课或亲子权限。

## 页面与权限

同步页显示「部分完成」警告、五类基础数据数量和三类跳过关系数量；文案明确说明任课范围、班级成员和家长子女关系尚未导入。教师考试管理、学生/家长成绩查询继续使用现有关系校验，缺少关系时保持拒绝或空结果，不提供管理员绕过或推断关联。

## 验证

- 后端测试覆盖同一数字 ID 的教师、学生、家长互不覆盖，以及重复同步幂等。
- 后端测试覆盖关系数据不落库、运行状态为 `PARTIAL`、跳过数量准确；公开 API 或基础数据失败仍为 `FAILED`。
- 前端测试覆盖部分完成警告和数量展示；构建与现有测试全通过后再部署。
- 部署后通过正常登录与同步按钮复验，检查运行状态和基础数据数量；不以关系数据缺失作为成功条件。

## 已知限制

这不是完整的关系同步修复。`main09` 的任课、学生班级及亲子关系仍不可用，因此依赖这些关系的考试授权、班级成员列表和家长子女成绩功能仍受限。要实现完整功能，后续需要基座提供可可靠关联的公开关系标识，并另行设计会话身份与人员主数据的绑定。
